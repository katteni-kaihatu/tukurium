## 記録は設計判断と根拠を残す

`guidelines/`には、次の実装でも使える判断や注意点を置く。
機能の使い方、長い調査資料、APIの詳細は`docs/`に置き、ここからリンクする。
同じ仕様を複数ページに全文コピーしない。

新しい知見は、まず既存のページへ追記する。別の主題として独立させる場合は、内容が分かる英小文字のファイル名を付け、この一覧にも追加する。

記述の状態は次のように区別する。

| 状態 | 意味 |
|---|---|
| 決定済み | 今後の実装でも維持する方針。変更時は理由を残す |
| 実装済み | コードと検証で確認した動作。関連箇所を示す |
| 改善案・未実装 | 次に検討する内容。現行機能の説明に混ぜない |
| 要確認 | 根拠や再現条件が不足している内容 |

外部の実装を参考にする場合は、資料のURLと確認日を残す。
資料で確認できたこと、コードからの推定、tukuriumで採用した判断を分ける。
解決していない疑問は「要確認」として記録し、仕様を確定する前にユーザーへ相談する。

## 不具合の記録は症状から探せるようにする

追記には次の情報を含める。すでに説明した設計原則は、該当ページへのリンクで済ませる。

- 症状と再現条件
- 確認できた原因
- 修正した動作と、その理由
- 再発を検出するテストや確認手順
- 関連コード・コミット、確認日

## この参照集で使う用語

| 用語 | 意味 |
|---|---|
| 共有状態 | Rustが確定し、参加者へ配信・保存するワールドのデータ |
| ローカル状態 | その端末だけの入力・表示・一時計算の状態 |
| WorldPanel | ワールドに置くパネルの共有Componentと、その表示面 |
| 表示モデル | UIが描画や操作に使うデータ。共有状態を基に端末内で組み立てる |
| 入力の占有 | ドラッグや文字入力を始めた対象へ、対応する入力を届け続けること |
| 編集リース | 共有フィールドを編集する人を一時的に決める仕組み |
