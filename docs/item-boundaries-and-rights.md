# ライセンスは保留し、先に作品の境界を整える

更新日：2026-10-24。対象：tukuriumの実装者と設計を検討する人。

**現時点ではライセンス機構の開発を保留する。** 複数の部品を一つの作品として扱う範囲を決め、保存・複製・再配置を成立させてから、作者や利用権の仕組みを検討する。
今回決めたのはこの順序であり、以下のデータ構造や細かな操作規則は設計案である。

ワールド内の共同操作は、作者・所有者やライセンスの値で拒否しない。保持・移動・回転・拡縮・編集・構造変更に対する制限は解除した。参加者の確認、値の検証、変更の競合チェックは維持する。
ライブラリの保存・取得・共有・再公開も、作者・所有者・ライセンスの値で拒否しない。公開・共有ダイアログから利用条件の選択欄を外した。
作者情報や保存データは残している。古い保存版や公開作品に利用条件が付いていても、現行の操作制限としては使わない。後から正式なライセンスを導入する際、今の操作許可をそのまま将来の契約や利用条件とみなさない。

サインイン済みの利用者は、IDが分かる保存版や素材を取得できる。個人ライブラリの一覧や名前変更・削除、公開停止、セッションの管理は引き続き本人が行う。保存先の実在、ハッシュ、形式、容量、リクエストの重複は検証する。
以前の[アイテム・ライブラリの設計案](item-library-workshop-design.md)と[実装計画](asset-library-implementation-plan.md)にある「初版から権限を入れる」という順序は、本メモで置き換える。

## 今のObjectRootと、作品をまとめるルートは役割が違う

コードにはすでに[`ObjectRoot`](../crates/core/src/components.rs)がある。更新番号、描画先のAddress、任意の`ItemIdentity`を持ち、各オブジェクトを管理している。
名前だけで「ここから下が一つの作品」と決まる仕組みではない。

[`Slot`](../crates/core/src/components.rs)の親子関係と、[`hierarchy.rs`](../crates/core/src/hierarchy.rs)の子孫の複製・削除もある。
ただし、どの親子のまとまりを独立した作品として保存するか、途中に別の作品が入った場合にどう扱うかは定まっていない。
現在の[ライブラリ保存](../crates/asset-server/src/lib.rs)は単一の`ObjectView`を受け取る形で、子孫を含む作品全体の保存とは分けて考える必要がある。

例えば机にランタンを置いたとき、机の子になっただけでランタンの作者や作品の単位まで机に統合されると困る。
位置関係を表す親子構造とは別に、「ランタンの外装・光源・スイッチ・Luaをまとめて扱う」という境界が必要になる。
この境界を表す Component として [`ItemBoundary`](../crates/protocol/src/library.rs)（`prefab_key` / `editing_prefab`）を追加した。親子構造とは別に Slot へ付け、Inspector は `editing_prefab` のときプレハブ編集帯を出す。ライブラリの境界単位保存への拡張は後続。既存の`ObjectRoot`の改名はしない。

## 作者、配置者、利用権、保持中の人を分けて考える

将来の情報は、次の役割に分ける案とする。今すぐすべてのComponentを追加する計画ではない。

| 情報 | 何を表すか | 変更する場面の例 |
|---|---|---|
| 作品の境界 | 一緒に保存・複製する部品の範囲 | 作品をまとめる、分割する |
| 作者と来歴 | 誰が制作し、どの作品・保存版から派生したか | 制作への参加、派生版の保存 |
| 配置した人・管理する人 | このワールドに置いた人と管理を任された人 | 配置、明示的な管理の引き継ぎ |
| ワールド内の操作権限 | 持つ・動かす・編集・削除を許す範囲 | セッションや作品の設定変更 |
| 取得した作品の利用権 | 保存・改変・再配布の条件 | 作品の取得、条件を伴う配布 |
| 保持・編集中の占有 | 今操作している人とその対象 | 保持開始、解放、切断 |

Aさんが作ったランタンをBさんが配置し、Cさんが運んでも、作者はAさんのままとする。
Cさんの保持は一時的な操作であり、それだけで管理者を変更したり、保存・再配布の権利を与えたりしない。
また、移動した履歴と、構造やLuaを制作した履歴は分けたい。

現在の[`ItemIdentity`](../crates/protocol/src/library.rs)には`creator_id`、`owner_id`、`source_version`、`permissions`、`editors`がある。
一つの`owner_id`を、配置の管理・移動の許可・ライブラリの取得資格に兼用している部分がある。
今後は各情報の意味を決め直す。既存フィールドがあることを、そのまま将来設計の制約にはしない。

作者情報は制作の記録として扱う。ファイルをアップロードした人を、その素材の原作者だと自動で認定する仕組みにはしない。
現行の同じHNを同じ利用者とする方式も、本人を厳密に識別する方式とは区別し、利用権を導入する段階で再検討する。

## 境界、保存、来歴の順に検証してから権限へ進む

以下は今後の実装を分けるための計画案であり、着手済みのタスクではない。

| 順序 | 検討・実装するもの | 確かめること |
|---|---|---|
| 1. 作品の境界 | 複数Slotをまとめるルート、境界内外の参照、作品の入れ子 | 机の子になったランタンを、独立した作品として選べる |
| 2. 保存と再利用 | 境界内の一括保存・複製・再配置、内部IDの付け替え、外部接続 | 二つ配置したランタンで、スイッチやLuaの参照が混ざらない |
| 3. 作者と来歴 | 作者、制作参加者、配置者、保存者、元の作品と版 | 他人が移動・複製・保存しても、元作者を失わない |
| 4. 操作権限と利用権 | セッションの操作規則、作品の利用条件、取得記録 | ワールドで動かせることと、保存・再配布できることを別々に判定できる |

保持中の占有や編集中の競合は、共同操作を成立させるために扱う。ライセンス完成を待つ前提にはしない。
共同操作の制限解除は、保持開始・ローカルと遠隔のプレビュー・確定操作の各経路に反映した。[回帰テスト](../tests/world-collaboration-integration.mjs)で、異なるユーザー同士の保持・回転・拡縮・編集と、作者情報の維持を確認する。

共有データはRustのComponentと登録表を通す。操作の許可はRust側で判定し、Godotの表示だけで制御しない。
Luaによる共有Writeも同じ判定に通す案とし、ローカルDriveの計算結果を作者情報や編集履歴へ毎フレーム記録しない。

## 作品の入れ子と保存範囲を先に決める

次に具体化する対象は、作品の境界である。次の論点を、小さなランタンの例で確かめる。

- 入れ子の作品は、ひとまず独立した境界を維持する案とする。外側を保存したとき、内側を含めるのか参照するのかは未決。
- 部品を境界の外へ移すことと、別作品へ組み込むことをどう区別するか。親変更だけで来歴を消さない方針とする。
- 内部の参照は複製先へ付け替える。外部参照は切断・再接続・明示的な依存のどれで扱うかを決める。
- 作品のまとめ直しや分割で、作者・来歴をどう保持するか。単一の作者IDだけで十分かも再検討する。

まず、ランタンを机に置く、取り外す、二つ複製する、保存して別ワールドへ配置する、という一連の操作を設計する。
この単位が固まるまで、ライセンスの種類や権限フィールドを増やさない。
